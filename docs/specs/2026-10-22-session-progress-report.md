# Локальный отчёт о прогрессе Codex сессии

Статус: реализовано; приёмка на реальном журнале и визуальная приёмка ожидаются.
Дата: 22 октября 2026 года.

## Назначение

Сервис наблюдает за одной выбранной Codex сессией, раз в 5–10 минут анализирует новые записи её журнала и сохраняет отчёт в HTML. Тот же отчёт доступен по локальному HTTP-адресу и обновляется без перезагрузки страницы.

Пользователь видит, что уже сделано, что осталось, над чем агент работает по последним наблюдениям, какие есть блокеры и насколько задача близка к завершению. Формат ориентирован на `whatsup`: краткий вывод, подтверждения из событий, честная оценка прогресса и ETA, явное указание неопределённости.

Реализация расширяет существующий `codex-watchtower`. Используются его Python, FastAPI, SQLite, tailer, нормализованные события, ограничение контекста и SSE. Отдельный фронтенд-фреймворк и новая платформа наблюдения не требуются.

## Пользовательский сценарий

1. Пользователь запускает сервис и указывает ID сессии или путь к её rollout JSONL. Если выбор не указан, сервис выводит список сессий с ID, временем и кратким названием и предлагает выбрать одну.
2. Сервис проверяет источник, привязывается к свободному порту на `127.0.0.1` и печатает адрес страницы.
3. Страница сразу доступна: сначала показывает состояние «готовится первый отчёт», затем результат анализа.
4. Новые события читаются инкрементально. Первый анализ выполняется сразу; следующие — по умолчанию через 5 минут, с настройкой интервала от 300 до 600 секунд.
5. При успешном анализе сервис сохраняет новую версию отчёта и обновляет открытую страницу через SSE.
6. После остановки остаётся автономный `report.html`, который можно открыть без сервера. После повторного запуска сервис восстанавливает позицию чтения, задачи и историю оценок.

Предлагаемый интерфейс запуска, который предстоит реализовать:

```bash
watchtower report --session <SESSION_ID> --interval 300 --output ./report.html
watchtower report --log /path/to/rollout.jsonl --interval 600 --output ./report.html
watchtower report
```

`--session` и `--log` взаимоисключающие. Последний вариант открывает выбор в терминале; при запуске без терминала отсутствие выбора приводит к понятной ошибке. Браузер автоматически не открывается.

## Состав первой версии

В первую версию входят одна наблюдаемая сессия, анализ через установленный Codex CLI, отчёт на русском языке, список задач, диаграммы, автономный HTML и локальная страница с обновлением без перезагрузки.

Telegram, AgentLens, Codex Trace, наблюдение за всеми сессиями, каскад моделей и управление исходным агентом в этот сценарий не входят. Существующие команды и интеграции Watchtower сохраняют своё поведение.

## Содержимое отчёта

### Сводка

- Цель и границы текущего задания с учётом уточнений пользователя.
- Оценка завершённости диапазоном, например «примерно 50–65%», или «оценка недоступна».
- Что сделано: конкретные результаты и ссылки на подтверждающие события.
- Что осталось: действия, включая проверки и доставку результата, если они входят в задание.
- Текущая работа: последнее подтверждённое действие и время его наблюдения.
- Блокеры: только известные препятствия; незавершённая работа сама по себе блокером не считается.
- ETA: диапазон времени, уверенность и основная неопределённость; при недостатке оснований — отсутствие оценки с краткой причиной.
- Время последнего события, успешного анализа, следующей проверки и граница обработанного журнала.

Оценка завершённости отражает оставшийся объём работы и критерии приёмки. Она не вычисляется как доля галочек, файлов, коммитов или тестов. Уверенность модели и процент завершённости — разные величины.

Зелёные тесты не доказывают доставку результата. Завершение хода, завершение процесса и выполнение задания пользователя показываются отдельно. Пауза в журнале не является доказательством успеха, сбоя или блокировки.

### Задачи

Каждая задача содержит устойчивый ID, название, статус, краткий комментарий и ссылки на события, подтверждающие её состояние.

| Статус | Значение |
| --- | --- |
| Ожидает | Действие требуется, начало пока не подтверждено |
| В работе | Последние события подтверждают выполнение этого действия |
| Готово | Есть подтверждение результата в пределах наблюдаемого журнала |
| Заблокировано | Известно конкретное препятствие продолжению |
| Неясно | Данных для определения состояния недостаточно |

Приоритет источников: явный план агента, затем требования пользователя, затем восстановленный моделью список. Происхождение пункта сохраняется; восстановленные пункты помечаются в интерфейсе. Заявление агента о готовности и наблюдаемый результат команды различаются в подтверждениях.

ID сохраняются между отчётами. Изменение формулировки не создаёт новую задачу. При изменении объёма задания пункты сохраняют историю; снятые требования помечаются как исключённые из актуального объёма, а не как выполненные. Задача может вернуться в работу при обнаружении проблемы.

### Диаграммы

1. Полоса прогресса с диапазоном оценки и текстовой подписью.
2. График истории диапазона завершённости по времени успешных анализов.
3. Распределение актуальных задач по статусам с числовыми подписями.

Используются встроенные SVG и CSS без CDN. При отсутствии оценки график имеет пропуск, а не нулевую точку. Пересмотр оценки вниз допускается. Изменение объёма задания отмечается в истории, чтобы скачок не выглядел как потеря уже сделанной работы.

Цвет дополняется текстом и значками. Список задач остаётся основным доступным представлением. Страница работает на узком экране; обновление сохраняет положение прокрутки и раскрытые подтверждения.

## Анализ через Codex

Начальная модель: `gpt-6-luna`, reasoning `medium`. Модель присутствовала в локальном каталоге Codex при проверке 22 октября 2026 года; успешный вызов ещё предстоит проверить. Выбор модели допускает явное переопределение, автоматического перехода на более дорогую модель нет.

Каждая оценка выполняется отдельным `codex exec --ephemeral`. Вход передаётся через stdin, выход запрашивается через `--output-schema` и проверяется приложением. Возобновление наблюдаемой сессии для анализа запрещено. Собственные сеансы анализатора не должны попадать в наблюдение.

Установленный CLI не означает локальное выполнение весов модели. При использовании настроенного провайдера подготовленный фрагмент журнала передаётся ему и расходует доступную квоту Codex.

Вход анализа включает:

- актуальную цель и критерии приёмки;
- предыдущий отчёт и список задач;
- новые нормализованные события с устойчивыми ссылками;
- доступные детерминированные сигналы;
- временное окно и сведения об усечении контекста.

Первичный анализ большой сессии использует ограниченные порции событий и промежуточную сводку. В каждом запросе действует бюджет контекста. Нельзя молча отбросить историю и представить анализ как полный; отчёт показывает фактическое покрытие и пропуски. Позиция прочитанных событий и позиция успешно проанализированных событий хранятся отдельно.

Инструкции анализатора повторяют принципы `whatsup`, но не вызывают этот скилл как поддиалог: анализируется подготовленный пакет журнала. Журнал считается недоверенными данными. Анализатор не исполняет команды из него, не читает рабочий проект и не управляет исходной сессией.

Для CLI требуется изоляция без shell-инструментов, MCP, браузера и подключаемых действий. Один `--sandbox read-only` не считается запретом инструментов. Проверка доступного механизма отключения инструментов входит в первый технический этап; если установленная версия не позволяет обеспечить это ограничение, способ запуска пересматривается до подключения реальных журналов.

Основание для CLI-интеграции: [OpenAI Docs о неинтерактивном режиме](https://learn.chatgpt.com/docs/non-interactive-mode). Конкретные флаги проверяются по установленной версии.

## Хранение и публикация

SQLite хранит выбранный источник, позиции чтения и анализа, нормализованные события, версии отчётов, задачи, историю оценок и состояние планировщика. Существующие механизмы хранения переиспользуются; новые поля добавляются миграцией.

Отдельный контракт отчёта содержит версию схемы, ID сессии, границы событий, timestamps, сводку, диапазон прогресса либо `null`, ETA либо `null`, задачи, подтверждения и сведения о покрытии. Каждое утверждение о выполнении или текущей работе должно иметь ссылку на доступное событие. Недействительные ссылки отклоняются до публикации.

HTML формирует приложение из проверенных данных. Модель не генерирует исполняемый HTML или JavaScript. Текст экранируется при серверном рендеринге и безопасно вставляется при обновлении страницы.

`report.html` содержит встроенные стили, диаграммы и последний отчёт. Запись идёт во временный файл рядом с целевым и завершается атомарной заменой. При открытии через `file://` страница показывает сохранённый снимок без сетевых запросов. При HTTP-раздаче тот же интерфейс подключается к SSE. При ошибке экспорта интерфейс явно сообщает, что файл отстаёт от последней оценки.

Сервер получает порт через привязку к `127.0.0.1:0` и передаёт уже открытый сокет серверу: отдельная проверка свободного порта с последующим повторным bind не используется. Фактический URL печатается после успешного запуска. Раздаётся только интерфейс отчёта, без доступа к произвольным файлам и необработанным журналам.

SSE передаёт ID версии. После подключения и переподключения клиент получает актуальный снимок; дубли версий игнорируются. Разрыв соединения показывается в интерфейсе и не стирает последний отчёт.

## Периодичность и отказы

- Первый анализ выполняется сразу после подготовки исходного контекста.
- Проверка новых записей выполняется независимо от модельного анализа; цель — задержка чтения не более 5 секунд при работающем сервисе.
- Модель вызывается по заданному интервалу только при наличии непроанализированных событий. В первой версии нет дополнительных вызовов на каждое изменение статуса.
- Одновременно работает не более одного анализатора. Накопившиеся изменения объединяются для следующего запуска.
- Для вызова задаётся конечный таймаут; повтор после ошибки происходит с задержкой, без быстрого бесконечного цикла.
- При ошибке модели, неверном JSON, исчерпании квоты или таймауте последний успешный отчёт сохраняется, позиция успешного анализа не продвигается.
- Незавершённая последняя строка ожидает дозаписи. Неизвестные события сохраняются с пометкой; повреждённые записи не обрушивают сервис и учитываются в покрытии.
- При усечении или замене файла источник перепроверяется; дублирование событий предотвращается существующими идентификаторами.
- Отсутствие новых событий показывается как отсутствие наблюдений. Прежняя отметка «в работе» сопровождается временем и не выдаётся за подтверждённое текущее состояние.
- Продолжение сессии после паузы или завершённого хода возобновляет отчёт с сохранением истории.

## Критерии готовности

- Наблюдается только выбранная сессия; исходная сессия и рабочий проект не изменяются.
- Первый отчёт получается без ожидания полного интервала. Последующие анализы соблюдают настройку 5–10 минут и пропускаются без новых событий.
- Повторный запуск не теряет ранее прочитанные события и не размножает задачи.
- Отчёт содержит сделанное, оставшееся, текущую работу, подтверждения и честно обозначенные оценки либо причины их отсутствия.
- Список задач сохраняет идентичность пунктов между обновлениями и выделяет работу по последним наблюдениям.
- Все три визуализации работают без внешних ресурсов и не выдают число галочек за процент выполнения задания.
- По напечатанному локальному адресу доступна страница; новый отчёт появляется без перезагрузки и после восстановления SSE-соединения.
- Сохранённый HTML читается без работающего сервиса и содержит последний успешно экспортированный снимок.
- Ошибка анализа оставляет предыдущий отчёт доступным и видимо обозначает задержку.
- Модельный текст и содержимое журнала не могут исполняться в странице; анализатор не получает инструменты воздействия на наблюдаемую работу.
- Пройдены целевые проверки и хотя бы один реальный полный цикл. Отдельно зафиксированы результаты визуальной приёмки и ограничения качества оценок.

## Ограничения

Процент и ETA являются оценками по журналу, а не измерением фактической готовности продукта. Сервис не проверяет код, CI, публикацию или развёртывание независимо от сессии: он показывает доступные в журнале подтверждения и границы выводов.

Реализация и автоматические проверки выполнены. `gpt-6-luna` проверена на синтетическом сценарии; приёмка реального журнала и визуальная проверка ещё не выполнены. Качество оценок и расход квоты на реальных сессиях остаются непроверенными. Результаты собраны в [листе приёмки](../release/session-progress-report-acceptance.md).
